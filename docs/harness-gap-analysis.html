clone-ai · audit · 2026-09-08

作为一个成熟的 harness agent，还缺什么

clone-ai 已经是一个认真的本地 Kernel：Journal 是真相，Worker 是黑盒，完成由证据决定。 它还不是一个可交付的 harness——控制面有洞，预算半真半假，隔离停在提示词，观测停在 console.error。

审计范围：src/ 14,842 行 · test/ 7,166 行 · UI 1,063 行 对照：Cursor / Claude Code / Codex 一类成熟 harness 的控制面，而不是聊天机器人清单 方法：读源码与测试，不跑 live 模型
评分卡 项目画像 已经很强 13 个差距 P0 / P1 / P2 README vs 代码 顺手发现的 bug 附录

一句话结论

把 clone-ai 当成「个人数字分身的 Kernel 骨架」是准确的；把它当成成熟 harness 会高估。 Kernel 的权威边界（提案 / 审批 / 证据 / 崩溃裁决）已经写进代码，而且有 kill-restart 测试托底。 缺的是 harness 把这些边界变成可操作、可观测、可隔离、可取消的控制面。 最危险的缺口不在模型，而在 loopback HTTP：本机任意进程可以批准 Run、全局安装 CLI。

已经很强的部分

成熟 harness 的内核契约，clone-ai 大部分已经写对了。差距分析不该假装这些不存在。

  • 权威边界清楚。 Main Agent 禁用内置 file/shell 工具（session.ts:108），propose_work_plan 只创建 Run；完成、审批、记忆提升都在 Kernel。
  • Journal 是真相。 SQLite WAL + synchronous=FULL（sqlite-journal.ts:26-27），事件可重放；claim 是可变所有权行，不是事件。
  • 崩溃故事完整。 lease 过期才回收孤儿 Run（runtime.ts:213-257）；可逆工作回队列，外部/不可逆/验证中途失败而不是重放副作用。队列每 tick 调用 recoverOrphanedRuns（run-queue.ts:112-113）。
  • 黑盒边界诚实。 不解析 Provider 协议；exit 0 不算交付；合同要求产物而 workspace 未变就是 no_artifact（black-box-cli-worker.ts:275-281）。Worker 不能记录 receipt（:104）。
  • 计划合同严格。 未知 executor 在提案时拒绝（runtime.ts:1304-1308）；风险下限由 capabilities 重算（:1507-1522）；子单风险不可高于父步骤（:1375-1379）；external/irreversible 强制 maxAttempts=1（:1408-1414）。
  • 机械规则，不只是提示词。 record_state / install_agent 用 ownerStated 核对所有者原话（kernel-tools.ts:198-210、:268-281）。记忆进入 Worker 前必须有 memory.recalled 审计事件。
  • 测试不是摆设。 43 个 node:test 文件覆盖 journal 不变量、kill-restart、workspace lease、黑盒超时、记忆治理、golden-path。TypeScript strict: true。

13 个差距维度

每条给出状态、证据、影响，以及建议接到已经存在的 seam上，而不是另起炉灶。

1. Agent Loop 控制

partial

Main Agent 的多步 LLM ↔ tool 循环完全在 Pi SDK 内。仓库只做一次 session.prompt(query) （clone-main.ts:46、run-main-query.ts:55）。没有 maxIterations、没有 token 预算、没有 AbortSignal。

WorkOrderBudget.maxModelCalls / maxToolCalls 在 assertBudget 里校验必须是正整数 （runtime.ts:1458-1471），黑盒 Worker 只执行 maxDurationMs（进程杀树）和 Runtime 的 maxAttempts。模型调用次数是装饰字段。

runMainAgentQuery 无互斥。companion 的 SSE 与 CLI 可以对同一 pi-sessions/main-agent 指针并发 prompt，SDK 会话文件没有 harness 级锁。

接到哪里： 在 createMainAgentSession 外包一层 turn/budget 计数；给 runMainAgentQuery 加文件锁或队列；要么在黑盒边界统计调用，要么删掉那两个预算字段，避免合同骗人。

2. Tool 层

absent in prod

src/core/tool-authority.ts 是一套完整的按风险授权、超时、按 operationId 取消、崩溃后 reconcile 的工具运行时。 全仓库唯一引用是 test/tool-authority.test.ts。生产路径里 Worker 的工具对 Kernel 不可见。

没有 MCP 宿主。没有工具结果截断（search_history 有 8k 上限，工具 JSON 原样返回）。 黑盒的「不要做网络/支付/破坏性动作」写在 Prompt 里（black-box-cli-worker.ts:307-309），是劝告，不是闸门。

接到哪里： 两条路选一条并写进架构：要么承认黑盒、删除或降级 ToolAuthority 以免文档撒谎；要么让可治理的本地工具走 ToolAuthority，CLI Worker 继续黑盒。不要两套故事并存。

3. 沙箱隔离

absent

Worker 在所有者真实 workspace 上 spawn（black-box-cli-worker.ts:142-150）。隔离只有：空环境 + 配方白名单（:447-475）、Windows 解析 .cmd 避免 shell 注入（:492-519）、硬截止杀进程树。

Checkpoint 是「相对路径 → 内容 hash」的 JSON（workspace-evidence.ts:9）。恢复可以 rerun / reconciled / blocked，不能把文件倒回去。没有 worktree、没有容器、没有 seccomp、没有 dry-run。

接到哪里： 先给危险步骤一个 git worktree 或临时副本，把 JsonWorkspaceCheckpointStore 从 hash 索引升级为可还原快照；容器是下一档，不是第一档。

4. 策略与授权

partial

DefaultPolicyEngine 27 行（policy.ts:11-26）：可逆允许，external/irreversible 要审批，已批准则放行。 README 的自主性阶梯 0–4、常设授权、预算/隐私策略都不存在。 ApprovalGrant.grantedBy 类型包含 "standing_policy"（contracts.ts:166），默认引擎从不走这条路。

有 POST /api/runs/:id/approve（companion-server.ts:813），没有 reject。 waiting_approval 会永远挂着。CloneRuntime.cancel() 存在（runtime.ts:425-456），HTTP 与 CLI 都没有入口。

接到哪里： POST /api/runs/:id/cancel 和 .../reject 直接调已有方法；CLI 补 clone-ai approve|reject|cancel|trace（README 已经把它们写成计划命令）。

5. 验证与证据

partial

EvidenceVerifier 用正则从步骤自然语言里抠文件路径和「包含 / contains」子串（verification.ts:38-71）。 点名了文件就打开读；其它标准记为 unverified，不假装通过。这是诚实的 v0.1，不是成熟验收。

结构冲突：external 步骤要求带 locator 的 receipt（verification.ts:107-111），黑盒 Adapter 的 evidenceKinds 只有 artifact 和 observation（black-box-cli-worker.ts:104）。 external-operator 角色因此会在验证关口结构性失败——除非走另一条能发 receipt 的 Adapter，而那条路不存在。Connector 只有只读 FileConnector。

接到哪里： 给「跑测试 / diff 审查」写成可执行 Verifier 插件；receipt 必须来自 Kernel 观察过的连接器，而不是 Worker 自报。在那之前，不要把 external 步骤标成可自动完成。

6. 记忆与上下文

partial

治理记忆是 SQLite 索引 + Markdown 正文，召回是 CJK bigram / 拉丁词面匹配（md-memory-store.ts:86-97、:224-264）。 README 自己承认这不是向量检索。没有提升时去重、没有冲突合并、没有 PII 管道（只有 public|private|secret 标签）。

LocalMemoryStore（JSON）仍在仓库里，与治理库双轨。 Situation briefing 在 createMainAgentSession 时编译一次并缓存（session.ts:57-63）。companion 每次 query 重建会话所以还新鲜；长寿命 CLI resume 会读到过期情境。

压缩依赖 Pi SDK；本仓库用 search_history 把被摘要掉的对话捞回来。Harness 自己不算窗口、不编 prompt 版本。

接到哪里： 先删或封死 legacy store；召回加一层 embedding 作为 rerank，而不是换掉可测试的 bigram；briefing 改为每 turn 重编译或设 TTL。

7. 模型层

partial

Planner 是可选的 OpenAI Responses API 裸 fetch（llm-planner.ts:109-128），强制 create_work_plan function call。 非法计划最多纠正一次（:46-77）。HTTP 429/5xx 没有退避：createWorkPlan 在 plan() 的 try 之外（:63），传输失败直接抛，不会进入纠正循环。

默认模型字符串是 "gpt-5"（:153）。Main Agent 的模型选在 Pi 的 agentDir，clone-ai 配置面管不到。 没有成本/延迟路由（capability-dispatcher.ts 注释里写了「未来再加入」）。没有 token / 美元账本。

接到哪里： 给 OpenAIResponsesPlannerModel 加状态码重试；把 Main Agent 模型写进 config.json；Journal 记 usage 事件，哪怕先从 Pi session metadata 抄过来。

8. 可观测性

absent

生产日志是 console.error（队列恢复、Run 失败）。没有 Pino，没有 OpenTelemetry，没有 metrics，没有 /health。 唯一轨迹是 Journal。坏案例落到 reporting/bad-cases.md，注释写「Langfuse 以后再说」（bad-case-log.ts:4-6）。

GUI 设置里有「审计与轨迹」，数据来自 Journal 事件映射（companion-server.ts:950、:1144），不是分布式 trace。

接到哪里： 最小集是 JSON 日志 + GET /api/health（journal 可写、queue 未卡死、sidecar 存活）+ 每个 Run 的 duration/status 计数。OTel 可以等真的有第二个进程。

9. 可靠性与运维

partial

队列、lease 续期、优雅 close() 停消费者，这些是真的。缺的是入口层限流： POST /api/main-agent/stream 没有排队、没有单飞（companion-server.ts:675-710）。 workspace 有独占锁，但没有全局「最多 N 个 Worker」配置。

desktop-sidecar.ts:21-22 处理 SIGTERM/SIGINT；companion:debug 路径没有。 没有 log rotation（.gitignore 忽略 *.log，代码不切分）。

接到哪里： 把 sidecar 的 shutdown 提进 startCompanionServer；stream 入口加 in-flight=1 或明确拒绝并发。

10. 安全

loopback ≠ auth

默认 host = "127.0.0.1"（companion-server.ts:70），请求体 32KB 上限（:1273）。 handleRequest 没有 token、没有 Origin/Host 校验、没有 CORS 白名单。 本机任意进程，或浏览器里一张恶意页面对 loopback 的 DNS rebinding，都可以调用 POST /api/runs/:id/approve、POST /api/agents/:id/install（npm global）、PUT /api/settings/providers。

Tauri csp: null（apps/desktop/src-tauri/tauri.conf.json:22-24）。 SMTP reporting.json 可存明文 pass；tlsConnect({ rejectUnauthorized: false })（smtp-sender.ts:87）。 没有 OS Keychain，没有加密 content store——这两项 README 写成了建议技术栈。

接到哪里： 启动时生成 loopback bearer，UI 与 CLI 自动带上；拒绝非 loopback Host；给安装与审批加第二因素（已有 quote-gate 只覆盖 Main Agent 工具路径，HTTP 按钮不经过它）。

11. 评估与质量门禁

partial

离线测试面很宽，但没有 .github/workflows、没有 eslint/prettier/biome、没有 coverage 脚本（.gitignore 里有 coverage/ 却从未产生）。 README 假设 CI 会跑 bench，仓库里没有 workflow。

benchmark/run.ts 五个任务（summarize / 两步链 / 三步管道 / code-tool / 预期失败）。 LongMemEval 离线召回：样本 recallAny@1 ≈ 0.72，@10 ≈ 0.93。没有 planner 质量回归、没有路由回归、没有 prompt 版本。

接到哪里： 一条 GitHub Action：npm test + typecheck。把 golden-path 固定为 harness 契约测试，比再写五个 bench 任务更值。

接到哪里： 日历只读是 Phase 2 的最小证明；写入必须产出 Kernel 侧 receipt。不要先做宽邮件访问（README 自己把这列为暂缓）。
